# Preliminary safety audit — Shopee Malaysia side-panel agent

**Status:** provisional, read-only preliminary audit; **not a final verifier verdict and not a whole-product PASS**.

**Audited source:** `C:/Users/wongn/Documents/Interview/Manus/tasks/4 - chrome agent extension with a side panel/.work/worktrees/architecture-20261024-YYvz4/extension`

**Inputs:** `requirement-delta.md`, owner `plan.md`, `handoff.md`, `implementation-report.md`, and the frozen extension source. This audit was limited to runtime wiring and serious safety/contract gaps. No product files were changed, and no shell, test, build, browser, navigation, or provider command was run. The implementation report's fixture-test claims and the absence of live Shopee/OpenRouter evidence are not treated as independent verification.

## Critical concerns

1. **The exact Malaysia-origin contract is not implemented.** `core/shopee.js:1-8` defines and exports seven country regions; `panel.js:3` renders all of them; `core/shopee.js:11-15` accepts every listed origin; and `worker.js:25,38` validates only the user-selected member of that multi-region list. The accepted delta requires the sole supported origin to be `https://shopee.com.my`, with other origins stopped. The current runtime can intentionally start on Singapore, Philippines, Thailand, Indonesia, Vietnam, or Taiwan, so this is a direct contract violation rather than a live-evidence gap.

2. **Raw page/user data is serialized into `chrome.storage.session`.** `worker.js:40-41` saves a run containing `intent` and the full bridge `snapshot`; `worker.js:51-53` and `worker.js:55,58` save later runs/results as well. `bridge.js:15-16` puts up to 16,000 characters of `document.body.innerText` into each snapshot, and `bridge.js:24` can put another raw `nextSnapshot` inside the action result. `core/store.js:5-6` writes the supplied run object without sanitizing it. This defeats the memory-only requirement for raw snapshots, page text, prompts/intent, field-related page data, and shopping details. The same store wrapper does not establish a trusted-context access level, and `worker.js` has no startup initialization that clears stale session state; it only clears on the explicit `CLEAR_SESSION` message (`worker.js:59`).

3. **Cart item, option, and quantity are model-asserted, not page-evidence-derived.** The actual bridge observer (`bridge.js:5-16`) collects generic links/buttons/inputs and page text, but never produces `productCards`, variant evidence, selected options, quantity evidence, cart feedback, or a cart fingerprint tied to a rendered product. The Shopee evidence helpers in `core/shopee.js:24-35` are not imported or called by `worker.js` or `bridge.js`. `core/contracts.js:26-30` accepts any plain `cartIntent` object, while `core/policy.js:15-19` checks only nonempty fields plus equality of `c.fingerprint` to the generic target fingerprint. It does not prove the item label/link, variant/options, quantity, region, or expected cart result came from the current page. Further, a normal `click` without `cartIntent` is approvable (`core/policy.js:15-20`), so there is no invariant that an add-to-cart click must carry exact cart evidence. A model can therefore supply plausible-looking cart fields without the required rendered-page basis.

4. **Synthetic action confirmation is not semantically re-observed or evaluated.** `bridge.js:21-24` returns `verified` for a fill merely when the local input value equals the requested string, and returns `unknown` for every click regardless of its `expected` condition. `core/engine.js:22-27` stores the action result and does call `deps.observe()`, but never compares the fresh snapshot to `action.expected`, a URL/content transition, a cart count/message, or the cart item/variant/quantity. `worker.js:52` only checks the post-action origin. Consequently search cannot be reported verified on the required URL/content change, and a genuine cart confirmation cannot become verified; the fresh observation is effectively discarded for outcome validation. The code does avoid falsely claiming click success, but it does not implement the required evidence-confirmation behavior.

5. **Approval dispatch lacks a fresh origin/policy recheck.** `worker.js:55` sends an approved action directly to `dispatchApproved`; `core/engine.js:30-32` dispatches the stored action; and `core/engine.js:17`/`core/policy.js:22-28` only compare the user-supplied digest with the digest saved when the proposal was created. There is no pre-dispatch re-observation, origin check, or recomputation of the approval digest against current page state. The bridge's stale registry fingerprint check (`bridge.js:18-23`) may stop some DOM changes, but it is the only freshness defense at that boundary and it cannot validate cart evidence or origin. A redirect/origin change between proposal/approval and dispatch is therefore not fail-closed at the authoritative approval boundary.

6. **Sensitive/checkout blocking is label-regex based and incomplete.** `core/policy.js:3,11-14` blocks a finite set of words and allows ordinary text fills; `bridge.js:10-12` marks only password/hidden fields and labels containing password, OTP, verification, card, or CVV as sensitive. Generic targets such as “Confirm order”, “Proceed”, “Continue”, address/contact/identity fields, or payment-flow controls without one of the listed words can remain actionable. There is no page-kind or target-role rule that blocks all login, identity, payment, checkout, order-confirmation, or verification controls. This gap survives the existing explicit “payment/login/CAPTCHA” notice and is not cured by the model system prompt (`core/model.js:10`).

7. **The model picker is still a hidden structured-only shortlist.** `core/model-catalog.js:16-27` rejects every catalog entry that lacks `structured_outputs` and `response_format`, and `core/model-catalog.js:39` returns only those entries. `panel.js:7-8` renders that already-filtered list and has no limited/incompatible handling for non-structured permitted text-chat models. The delta requires all permitted live text-chat choices to remain visible, with accurate capability limits; structured capability may influence the cheapest default but may not hide choices. The exact GPT-generation and literal Claude Fable-generation exclusion predicate is shared by catalog validation and outgoing selection (`core/model-catalog.js:6-14,47-50`), so the concern here is the omitted permitted choices, not a claim that those two predicates are absent.

8. **Finish evidence is not checked, even though this branch does not currently turn it into success.** `core/contracts.js:41-43` accepts arbitrary `evidenceRefs`, and `worker.js:48` accepts any model `finish` by moving the run to `PARTIAL` with a generic local message. It does not match evidence references to fresh observations or action results. This is not a direct success bypass in the current code—the phase is `PARTIAL`—but the model's finish claims are not evidence-bound and should not be treated as completion evidence by later UI or integrations.

## Runtime wiring observations

The main proposal path is real rather than a fixture-only stub: `worker.js:45-51` calls `core/model.js:5-23`, which validates the selected catalog entry and performs the non-streaming OpenRouter request with a worker-side Bearer header. Search/fill/click proposals are routed through `advanceRun`, local policy evaluation, one-use approval, and `dispatchApproved` before `bridge.js` executes them. The approval and action-type boundaries therefore exist, but the evidence, origin, storage, and outcome defects above remain material.

The UI does provide a masked key field and a first-use statement (`panel.html:6,9`), and it does not claim provider-wide zero retention. `worker.js:26-29` keeps the raw key in worker memory and stores only `keyConfigured` in its model-config record. Those are useful boundaries, but they do not remediate the raw run serialization or missing startup session purge.
